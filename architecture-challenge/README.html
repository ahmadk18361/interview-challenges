Architecture Challenge

Overview

This is a design exercise, not a coding exercise. You will read a description of a system, select one problem from the list below, and write an Architecture Decision Record (ADR) describing your proposed change and the reasoning behind it. A 60-minute review session follows.

The expected effort is approximately 2 hours. Complete treatment of one problem is more useful than partial coverage of several. You are not limited to 2 hours; however, we do not want you to feel obligated to spend more than that. If you reach the time limit before finishing, note what remained unaddressed and submit what you have.

The ADR should be delivered prior to the start of the review session. This is a deliberately short window and the scope is set accordingly — we are not expecting a document that took a full day to produce. If 24 hours does not work around your current commitments, let us know and we will move the session. Asking for more time is not held against you.

You may send questions to your interviewer at any point before the session. We will answer within the same business day. Requesting information you do not have is a normal part of this exercise and is not counted against you.

System Description

A public-facing Claims Status and Document Upload feature set on a large government site. Authenticated users check the status of a claim and upload supporting documents.

Traffic

Approximately 180,000 authenticated sessions per weekday, peaking between 9 and 11 am ET. The status page accounts for approximately 70% of API traffic.

Known Issues

1. LEGACY-CS latency propagates to authentication failures

When LEGACY-CS stalls, status aggregation blocks while waiting for a response and the status page times out. Users refresh. Because eligibility is re-checked on every request, the resulting retry volume consumes the organization-wide IDENT rate limit, which produces login failures for all users — including those who never requested claim status. This has escalated to a site-wide incident approximately once per month.

2. No caching of status data

A product decision made approximately three years ago requires status to be read live on every request, with no cached or stale values served. The decision has not been revisited. No record exists of who made it or what it weighed.

3. Document upload failures discard the file

The SPA POSTs the file to DOCS-API through the BFF. On a 500 response from DOCS-API, the user receives a generic error and the file is not retained, so the user must locate and upload it again. This affects approximately 0.4% of uploads and is the second-largest category of support tickets.

4. Release coordination bottleneck

Staging is shared with the contractor that owns LEGACY-CS, so each release requires scheduling with a team outside your control. Releases are nominally every two weeks and frequently slip.

Constraints

  • LEGACY-CS cannot be modified, and the owning contractor's roadmap cannot be influenced within the timeframe of this work.
  • The system operates within a FedRAMP Moderate boundary. Adding a managed service not already inside that boundary requires an ATO amendment, currently running 6–10 weeks.
  • Persisting claim data at rest requires a privacy review, currently running approximately 4 weeks. The review may return conditions.
  • Team composition is 5 engineers, 1 designer, and a product manager shared with another team.
  • No additional headcount is available this fiscal year.

Task

Select one of the following and write an ADR:

A. Prevent LEGACY-CS degradation from causing authentication failures for unrelated users.
B. Prevent document upload failures from discarding the user's file.
C. Re-evaluate the no-caching decision described in issue 2.
D. A different problem in this system, if you judge it higher priority. State the basis for that judgment relative to A, B, and C.

Deliverable

One ADR, in any reasonable format. Length is 1 to 2 pages. Given the time window, brevity is expected — a longer document is not a better one. Diagrams are optional. No code is required.

Your ADR must include the following sections:

Context — Current state, what makes a decision necessary now, and what you are optimizing for.
Options Considered — At least two rejected alternatives, with the reasons for rejection.
Decision — The proposed change, specified in enough detail for an engineer to begin implementation.
Consequences — Expected improvements, expected regressions, and new risk introduced.
Rollout — How this ships given the constraints above. A few sentences on sequencing is sufficient.
Verification — One or two metrics indicating the change worked, and the threshold at which you would revert it.
Open Questions — Outstanding unknowns, and who would be able to resolve them.

Supporting material such as notes or sketches may be included if you have them. This material is optional and is not scored.

The system description above is incomplete in some cases deliberately, to allow for solution flexibility. Where information is missing, either ask us or record the assumption you made and proceed.

Review Session

60 minutes, with two or three members of the team.

~15 min You present the ADR.
~40 min Questions covering rejected alternatives, behavior under failure, delivery sequencing, and how the decision changes if a constraint changes.
~5 min Your questions for us.
